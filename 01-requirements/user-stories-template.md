## 1. 估算口径

- 人天表示投入工作量，不等同于日历工期；
- 每个Task只归属一个US，避免重复计算；
- 默认包含实现、自测和必要文档更新；是否包含02设计、04系统测试需明确；
- 估算必须记录假设、角色和风险，需求阶段采用ROM估算时标注误差范围；
- 需求变化后同步更新Task、依赖关系、顺序和人天。

## 4. 用户故事

### US-001 `<故事标题>`

#### 4.1 描述：

【AS】`<用户角色>`  
【I want】`<希望获得的能力>`  
【so that】`<可验证的业务价值>`

三个标签必须逐行保留，不得改写成“作为……我希望……以便……”的单句故事。

#### 4.2 验收标准：

**场景1：`<场景名称>`**  
【Given】`<初始上下文及全部前置条件>`  
【When】`<唯一主要行为或事件>`  
【Then】`<首要结果及其他可观察、可验证结果>`

如有多个场景，按“场景2、场景3……”重复完整的`【Given】→【When】→【Then】`三行。至少覆盖正常、异常、边界、权限和重复操作；不适用时说明理由。不得使用Gherkin代码块或大写英文关键字替代上述标签。

#### 4.3 业务规则：

#### 4.7 Definition of Ready

- [ ] 用户价值、范围和验收场景明确；
- [ ] 业务规则、依赖和执行顺序已识别；
- [ ] Task可独立执行并具备交付结果；
- [ ] 人天估算及假设已记录；
- [ ] 无阻止进入设计或开发的未决问题。

#### 4.8 Definition of Done

- [ ] Task全部完成；
- [ ] `【Given】/【When】/【Then】`验收标准全部验证；
- [ ] 需求、设计、代码和测试追溯完整；
- [ ] 无未接受的严重或重要问题；
- [ ] 产品负责人确认业务结果。
