# 文档控制、编号与版本规范

## 1. 文档状态

`草稿 → 编写中 → 待评审 → 整改中 → 已评审 → 已基线化 → 已废弃`

只有用户通过阶段卡点后，当前阶段成果才能标记“已基线化”。

## 2. 编号规则

格式：`<阶段>-<类型>-<序号>`。

示例：

- `REQ-SRS-001`：需求规格说明书；
- `REQ-US-001`：用户故事集；
- `DES-ARCH-001`：架构设计；
- `DES-DETAIL-001`：详细设计；
- `DES-API-001`：API设计规范；
- `DES-DB-001`：数据库设计；
- `DES-UX-001`：UX设计；
- `DEV-STD-001`：编码规范；
- `DEV-UT-001`：UT设计；
- `DEV-CR-001`：代码评审记录；
- `DEV-GIT-001`：Git工作流；
- `TST-PLAN-001`、`TST-CASE-001`、`TST-REPORT-001`、`TST-PERF-001`、`TST-RTM-001`；
- `REL-DEPLOY-001`、`REL-CHECK-001`、`REL-MYSQL-001`、`REL-NOTES-001`；
- `REV-FINAL-001`：专家视角评价报告。

## 3. 版本规则

- `v0.x`：阶段执行中的草稿；
- `v1.0`：首次通过用户卡点的基线；
- `v1.x`：不改变已确认目标的修订；
- `v2.0`：范围、接口、架构或验收基线发生显著变化。

任何修订必须记录变更原因、问题编号、修改章节、修改人和日期。

## 4. 适用性

- 必填：本阶段必须产出；
- 条件必填：技术或业务条件成立时必须产出；
- 可选：由用户或专家建议启用；
- 不适用：不参与完整性判断和评分，但必须记录依据。

“未填写”和“不适用”不得混用。
